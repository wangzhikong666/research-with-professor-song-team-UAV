# RGB–Depth 注册：SDK 路径和三组人工对应点初检

## 本次范围

用户要求在说明 USB 控制器影响后，继续核实 RGB 与深度的对应关系。当前 xHCI 下原有深度通道、RGB 预览和权限均可用，不因控制器切换假定像素已经对齐。
本轮完成真实参数与能力查询、统一镜像、启停 SDK 硬件 D2C、保存未注册基线及注册输出、三组人工图像特征对应点检查。
结论为当前静态场景的初步像素对应已完成检查，观测差为 1–5 像素；完整标定正确性、毫米级 XYZ 准确度与硬件同步仍未验收。

## 与双目、相机外参的关系

Astra Pro Plus 使用红外结构光生成深度；RGB 图像用于提供可见光外观。当前操作不是用 RGB 和深度图作为两幅普通照片重新做双目三角测距。
两路光学坐标系之间的相对旋转、平移确实属于相机外参，处理流程为：

`深度像素 + 测得的Z → 深度相机三维点 → 相机间R,t → 彩色相机三维点 → RGB像素`

除外参外，还需要两路各自的内参、畸变、实际分辨率/裁剪、镜像状态；场景有运动时还需要处理采集时间差。
相机到相机外参不同于将来相机到机械臂基座的外参。

## 实查参数与 SDK 接口

`data/registration-inventory-001/registration_inventory.json` 保存本次设备实际参数，640×480 深度、1 mm/计数、未注册、镜像关闭。

| 数据 | 本机返回 |
| --- | --- |
| depth/IR 工厂 fx,fy,cx,cy | 580.213806, 580.213806, 321.848450, 236.663773 |
| color 工厂 fx,fy,cx,cy | 542.721313, 542.721313, 324.996826, 235.307556 |
| 平移字段 | (-24.922857, -0.067444, -1.756615)，与当前 SDK 深度 mm 量纲数值一致 |
| 平移向量长度 | 约24.985 mm；为工厂参数值，不是尺量得到的实测基线 |
| 旋转矩阵行列式 | 约0.999999951 |
| 旋转正交性最大元素误差 | 约4.48e-8 |
| hardware DEPTH_TO_COLOR support | true |
| PIXEL_REGISTRATION 旧接口 | status=4，不支持 |
| PIXEL_D2C_REGISTRATION | status=0，三组查询均成功 |

`OBCameraParams` 结构把旋转/平移字段命名为 `r2l_r/r2l_t`；不能仅据名字自行取逆。
用已知输入深度像素和合成 Z=1000 mm 查询新 D2C 接口，输出分别为 `(311,237)`、`(105,105)`、`(480,340)`。
用工厂内参、该旋转/平移直接从深度点变换并投影，结果向下取整后逐个与 SDK 一致；取逆则不符。因此在本次 API 约定下，这些字段按深度→彩色方向使用有数值证据。
这些是接口几何测试，不是把合成 Z 当作物理测量；三个例子的匹配也不能证明整个图像和所有距离的畸变已经验证。

支持判断和接口声明来自现有 OpenNI 包内 `OpenNI.h`、`PS1080.h`、`OniCTypes.h` 及 SimpleViewer 源码。未安装 ROS 或新 SDK，也没有复制/提交第三方头文件。

## 真机模式与数据保护

- `astra_registered_open` 在启动流前临时设置 `IMAGE_REGISTRATION_DEPTH_TO_COLOR`，要求返回 mode=1、640×480、镜像关闭。
- 原有 `astra_point_open/astra_depth_open` 现在明确设置 mode=0，防止先前注册状态影响普通深度程序；关闭会话也请求恢复 OFF，不写 Flash 或升级固件。
- 已实机依次打开注册与未注册模式各35帧，读回分别为1/0、镜像均 false，均有非零深度。
- `DepthCamera(registered=True)` 只用于像素映射检查，**拒绝调用原始深度 XYZ 转换**。注册像素属于另一像素域，其 Z 所属度量坐标约定也尚未独立核实，不能把原深度 fx/cx 套到注册图上。
- 普通 `DepthCamera()` 保持原始深度模式，之前的 SDK XYZ 坐标约定不变。已通过原有8项深度质量与10类前景离线检查，并对之前保存的真实空/物/空图像重放，前景算法结果仍正确。这不是在新摆位下重复移走/放入实机验收。
- SDK 通用 DepthToWorld 的主点与工厂主点差异仍存在；本次 D2C 像素接口与工厂模型数值一致，不等于两条 API 可以无条件混用。

先在 `data/rgbd-raw-baseline-001` 保存未注册、非镜像深度和 UVC RGB，再在 `data/rgbd-hardware-d2c-001` 保存硬件注册结果。原深度 PGM 与注册输出分开命名、记录，后者不称作原始未处理深度。
本程序不启用软件补洞，也不把无效值当作目标位置；SDK 硬件注册内部的采样/重投影处理仍属于其输出定义。

## 三组人工点检

用户在左侧注册深度图点选清楚的特征后，程序冻结当时的深度/RGB图像，并关闭右侧绿色叠加线；再由用户在原 RGB 图选择同一个物理特征，减少绿色线提示造成的选择偏差。
存盘保留该冻结帧的 PGM、无叠加 RGB、叠加诊断图与元数据，后续点击不会更换原图。

| 组 | 注册深度像素 | 用户指认的RGB像素 | RGB−Depth | 像素距离 |
| --- | --- | --- | --- | ---: |
| 1 | (172,279) | (168,276) | (-4,-3) | 5.0 |
| 2 | (438,165) | (439,165) | (1,0) | 1.0 |
| 3 | (312,356) | (315,352) | (3,-4) | 5.0 |

三个值的均值约3.67像素、均方根约4.12像素。这里包含人工点击误差，只有一个静态场景的3点，**不是标准标定板的重投影RMSE，更不是毫米级 XYZ 误差**，不能据此宣称整幅 RGB–Depth 高精度对齐已验收。
已逐组读回 uint16 PGM、RGB图及记录，核对原始深度值、点坐标与像素距离一致。结构化证据见 [本轮核对JSON](rgbd-registration-check-2026-11-01.json)。

## 时间与操作

UVC 彩色由独立线程持续读取，使用最新可用的主机返回时间与深度主机返回时间配对，差值不超过0.2 s、实时显示时两者年龄不超过0.5 s；超时显示等待，不沿用过期图作为实时画面。
这是主机时间筛选，不是曝光同步。自动注册快照的主机返回时差约18 ms，也不能把它当成曝光时差。所有检查依赖相机和场景静止。
本次注册预览日志仍有1条 JPEG 数据段提前结束警告；选定保存图可读、人工对应点已核对，不等于全部彩色帧均无解码异常，RGB长期可靠性仍未验收。
冻结图可用于人工对应点标注，明确标注为历史帧，不输出用于执行的 XYZ。

```bash
bash scripts/build_ir_preview.sh
# 只读参数、能力、原始深度和 SDK 像素接口查询
.venv/bin/python camera/astra_pro_plus/registration_inventory.py --output data/registration-inventory-new
# 当前模式 RGB 与深度预览；先关闭其他占用相机的程序
.venv/bin/python camera/astra_pro_plus/rgbd_registration.py \
  --output data/rgbd-registration-new --seconds 180
```

左图为注册深度，右图为 RGB；`E` 切换绿色深度有效区域边缘叠加（只是诊断线，不是独立校准证据）。
左键先点左图有有效深度的特征，再点右图同一物理特征。`Esc` 取消冻结，`S` 保存，`Q` 退出。
`--raw` 用于未注册基线。数据图像留在本地 `data/`，SDK及二进制仍不上传。

下一步是把指定的 RGB 目标区域对应到原始深度中的有效表面点，保持清晰的像素域和坐标系。对齐精度、畸变状态、物体姿态、相机到机械臂基座标定及实际抓取分别保持原有未完成状态。
