# 彩色异常：如何区分硬件与采集链路

最新进展：USB 控制器改为 xHCI 后，真实彩色预览恢复；[本次验证](rgb-xhci-validation-2026-11-01.md)记录正常画面、并发采集和仍存在的帧率/解码警告限制。本文保留此前故障对照，不用旧失败结果覆盖新证据。

记录日期：2026-11-01。Windows 原生彩色对照已由用户确认正常、连续更新；当前优先排查 VMware/Ubuntu 采集链路，不据此诊断相机损坏。一次正常测试仍不能完全排除间歇性问题。

## 已知证据

- 深度接口可启动、可预览、可保存有效区域的原始深度，但接收速率低于标称。
- 彩色 USB 可枚举，V4L2 可协商配置；MJPEG 图像损坏，YUYV 出现超时或绿色条带。
- 050f 单设备权限已获批准并应用。官方 libuvc 现能打开设备，协商 640×480 MJPEG 30 FPS 并报告流启动成功。
- 两轮官方例程分别运行 10 秒和 30 秒，均没有返回图像数据日志；由外部时限结束。具体结果见 [结构化记录](color-libuvc-2026-11-01.json)。
- 用户已完成 Windows 原生相机应用对照，反馈“外接相机画面正常、连续更新”。这是用户报告，代理未直接操作或观察 Windows。
- 对照要求保持线缆及物理 USB 接口不变；用户未另行报告改变这些条件。Windows 使用的分辨率、格式和帧率尚未记录，不能当成完全相同流配置的比较。
- 未进行换物理接口或换线对照，目前不必优先更换硬件。
- Windows 对照后 050f 曾交回主机；用户随后关闭 Windows 相机并重新将 050f 交给 Ubuntu。当前重新枚举为 Bus 002 Device 006，uvcvideo 正常绑定，video0/video1 已恢复。
- 虚拟 USB 控制器仍为 VMware USB2 EHCI [15ad:0770]，480M；没有改变控制器设置，尚无 xHCI 对照。
- VMware Tools 为 12.3.5.46049；这是客体工具版本，不能当成 Windows 宿主机 VMware Workstation 的版本。

深度与彩色是独立采集通道，因此深度正常不能排除彩色模块单独故障。
条纹和坏 JPEG 只能说明当前收到的数据异常，不能仅凭外观区分相机输出、连接传输或软件处理环节。
USB 设备可枚举也只说明控制通信能工作，不能证明持续视频流可靠。

## 最小对照顺序

1. 已完成：应用已批准的 050f 权限，停止其他彩色进程，运行包内官方 ColorReaderUVC。
2. 官方例程返回图像数据时继续检查非零长度、解码和实际画面；打印“收到数据”不代表画面可用。
3. 已完成：用户将彩色 USB 设备交回 Windows，原生相机应用中外接彩色画面正常、连续更新。
4. 若 Windows 也异常，再单独更换物理 USB 接口。可以直连时不经过额外 Hub。记录每次只改变的一个条件。
5. 仅当线缆可更换且有匹配规格的线时，再单独换线复测；不拆机、不强行拔固定线缆。
6. 需要时在另一台原生系统电脑复测，或联系厂商确认。

重新接入后的 V4L2 MJPG 640×480、30 FPS 协商成功，10 秒测试仍有 JPEG 损坏警告；保存帧近黑，带有纹理/点状异常，不是用户所示正常彩色图。返回帧计数速率异常，不能作为传感器实际 FPS。数据位于 `data/color-after-windows-001/`，日志为 `logs/color-after-windows-001.log`。

## 黑白画面与彩色权限的区别

用户报告先前 NiViewer 中看到两幅实时黑白画面，并提供了一张正常有色外接相机画面的截图。
通过新编译的只读 `sensor_inventory` 实际查询，OpenNI 报告：

- DEPTH: exposed。
- IR: exposed。
- COLOR: not exposed。

因此当前 OpenNI 的 NiViewer 与独立 UVC 彩色采集不是同一条数据通道。用户随后提供两张 NiViewer 截图，结合流查询可确认首张左侧为深度伪彩色、右侧为红外灰度图；第二张主要显示深度。黑白显示本身不是权限错误。
当时权限错误的证据是程序返回 Access denied；两设备规则现已应用，权限错误已解决。
深度常以灰度或伪彩色显示距离，红外灰度显示的是红外强度，都不能据此当成可见光 RGB。
`sensor_inventory` 输出中的设备名为驱动通用名称 Orbbec / Astra，不改变机身 Astra Pro Plus 与 PID 的确认结果。
查询日志位于 `logs/sensor-inventory-001.log`。截图底部显示 Image registration is off，确认本次显示未启用图像注册。
底部 Capture Formats 的 Depth: Lossless / Image: Lossy / IR: Lossless 是录制格式配置，不能仅凭其中 Image: Lossy 推定当前有可用彩色帧。
深度图有大面积黑色缺失，黄色区域是距离的显示映射而非物体可见光颜色；单凭截图不能计算距离、有效比例或定位精度。
当前画面主要观察显示器及周边，红外画面中屏幕区域较暗，局部反光很亮。这提供了场景/红外回波问题的线索，但不能据此确定深度缺失的唯一原因，也不能因此忽略此前采集节奏和 RGB 异常。
下一步先把哑光纸箱或纸板放到中央约 0.6–1 米，采集其原始深度，再决定是否有必要深入调整虚拟 USB。

原理参考：[Orbbec 结构光说明](https://www.orbbec.com/blog/structured-light-vs-itof-depth-cameras/)介绍通过已知红外投影图案恢复深度，测量受图案可见性、表面和环境影响。该原理支持做受控场景对照，不足以对当前故障归因。
若 Windows 应用无法打开设备，先检查设备是否交回主机、所选相机和隐私权限；“打不开”本身不能直接判为硬件故障。
同一时刻只让一个程序占用彩色接口。测试后由用户重新在 VMware 连接设备，代理复查 PID 和权限。
官方 libuvc 测试结束后已确认没有采集程序残留。其测试后 050f 的 Linux 内核驱动暂未绑定；
之后恢复 V4L2 时需通过 VMware 重新转接使设备重新枚举，并确认 uvcvideo 绑定，避免混淆驱动状态与硬件故障。

## 结果的解释

| 对照结果 | 更值得排查的方向 | 仍不能证明的事 |
| --- | --- | --- |
| Windows 彩色正常，VMware 异常 | 虚拟化 USB、Ubuntu UVC/采集接口 | 不能仅凭一次正常排除间歇性硬件问题 |
| 官方 libuvc 正常，V4L2 异常 | 两条软件采集路径的差别 | 仍需长时间验证及实际图像检查 |
| 换物理接口或线后恢复 | 端口、连接、线缆、供电条件 | 不能据此确认是哪一个电气因素 |
| 原生系统与多个连接条件均持续异常 | 彩色模块或设备内部硬件的嫌疑增加 | 仍需厂商/进一步对照才能确诊 |

Windows 正常而虚拟机异常的结果已出现，故排查优先级转向虚拟化 USB 与 Ubuntu 采集路径；尚未定位具体哪一层出错。
当前不升级固件、不修改 UVC 驱动参数、不更换多套 SDK。
