# xHCI 对照：RGB 正常预览恢复，双路采集可工作

## 变化及作用

用户在 Windows Workstation 17.5.0 build-22583795 中，将虚拟 USB 兼容性从 2.0 改为 3.1，正常关机、重新开机并将两路相机连接回 Ubuntu。
实查当前彩色 `2bc5:050f` 和深度 `2bc5:060f` 均挂在 `xhci_hcd` 下，仍为 high-speed 480M；旧 EHCI 控制器也仍存在，但相机的实际路径已切到 xHCI。

改变的是虚拟机的 USB 主控制器与传输处理路径，不是相机的 USB 协议、光学结构、固件、分辨率或精度。USB 2.0 相机挂在 xHCI 下仍显示 480M，不应据此认为切换失败。
这也与 [VMware 的通用 xHCI 设备兼容说明](https://knowledge.broadcom.com/external/article/307817/host-and-guest-os-usb-30-and-virtual-xhc.html)中可管理 USB 1.1/2.0/3.0 设备的说明一致；该资料包含旧版兼容性条件，本文针对 Workstation 17.5 的状态以本次实查为准。
两设备现在分别为 Bus 003 Device 006（彩色）和 Device 005（深度），总线号与切换前不同；已有按 VID/PID 匹配的权限规则仍生效。视频节点仍为 `/dev/video0`，具备用户读写 ACL。

本轮结果支持在此环境保留 USB 3.1 配置作为可用采集路径。由于同时伴随关机、重启和重新枚举，且未回退 EHCI 复现，尚不能确定某一具体 VMware/UVC 缺陷或将恢复完全归因于控制器本身。

## 实测结果

所有本轮数据均来自真实相机，未使用离线模拟图替代。

| 项目 | 结果 |
| --- | --- |
| 同配置 MJPG 320×240 原始缓冲对照 | 30/30 可解码，30 个不同哈希，全部原始 JPEG 起止标记及图像尺寸检查通过 |
| EHCI 切换前最近同配置 | 30 个缓冲仅 2 个可解码，实际查看均严重竖条，无可用画面 |
| xHCI 640×480 MJPG 实时预览 | 30.051 秒，485 帧，读取失败 0 次，主机接收约 16.70 FPS |
| 预览确认 | 用户确认颜色正常且随手部动作连续更新；代理查看保存图像正常 |
| 并发彩色（独立 UVC 通道） | 15.047 秒，235 帧，读取失败 0 次，主机接收约 16.74 FPS；保存图像正常 |
| 并发深度（独立 OpenNI 通道） | 300 帧，设备时间跨度 10.535 秒，接收约 28.38 FPS；无整帧全零、无 SDK 帧序号缺口 |

彩色实际格式为解码后的 BGR uint8，原始传输为 MJPG；深度为 640×480 DEPTH_1_MM、1 mm/原始计数，保存未缩放未滤波的 uint16 PGM。
已读回深度 PGM，核对 dtype、分辨率、中心原始值及有效比例与报告一致；已读回两段 640×480 彩色图，代理视觉检查正常。

### 保留的限制

- 30 秒彩色预览日志有 **1 条** `Corrupt JPEG data: 8652 extraneous bytes before marker 0xd8` 警告；并发彩色段未出现此类警告。不能将本轮写成全程无解码警告，也未逐帧人工审查全部 485 张图。
- 请求流为 30 FPS，彩色程序实测接收约 16.7 FPS；这不是已证明的传感器曝光帧率，原因尚未定位。深度并发段最大设备帧间隔约 0.600 秒，不能仅凭序号连续宣称没有时间间隔异常。
- 当前通过的是短时真实彩色预览恢复和双路数据可读取，不是长时间高可靠采集验收。
- 并发采集不等于同步帧对。彩色是主机读取返回时间，深度是设备时间，两者尚未统一时钟，也未启用硬件同步。
- 两路即使都是 640×480，像素也未对齐。该深度探针使用 SDK 默认 `mirroring=true`，彩色图未水平翻转；在保存预览中左右方向不同。自动定位/深度点选代码此前使用镜像关闭，两种模式不可混用。下一步应统一方向并核实标定及映射。
- 当前深度固定中央像素为 0，中央 ROI 非分割目标，不能将其约 4.3 m 的有效样本中位数当成书包距离。该记录只验证采集通道，未做目标测量。
- SDK 与工厂主点差异、畸变状态、绝对准确度及相机到机械臂坐标变换仍未验收。

## 产物与复现

- `data/color-xhci-mjpg320-001/`：同配置原始 JPEG 缓冲、解码分析、视觉检查。
- `data/color-xhci-live640-001/`：30 秒预览报告、真实彩色 PNG、用户确认记录。
- `data/color-xhci-concurrent-001/`：并发彩色报告和 PNG。
- `data/depth-xhci-concurrent-001/`：并发原始深度首/中/末帧、逐帧 CSV、流配置、分析报告。
- `docs/rgb-xhci-validation-2026-11-01.json`：可进入 Git 的结构化验证摘要；现场图像与原始数据按既定规则留在本地 `data/`。

```bash
# 仓库根目录；关闭其他彩色程序，输出目录必须新建。
bash scripts/capture_color_gstreamer.sh data/color-xhci-new MJPG 320 240
.venv/bin/python camera/astra_pro_plus/uvc_check.py --seconds 30 --fourcc MJPG \
  --width 640 --height 480 --fps 30 --preview --output data/color-preview-new
```

本轮未安装新 SDK/驱动、未升级相机固件、未改全局网络或 Python 环境。Ubuntu 22.04.5 与现有软件确实可以采集可用彩色图，不再以“Ubuntu 22.04 整体不支持”为诊断结论。
OpenNI COLOR 暴露方式与官方 ColorReaderUVC 的早期失败记录未被追溯改写；本轮恢复的是已验证的 V4L2/GStreamer/OpenCV 路径，官方 libuvc 示例尚未在 xHCI 下复测。

下一步主线：统一采集方向、核实当前模式内参/外参和 RGB–Depth 像素对应，再将彩色目标区域映射到有效深度，保留现有质量拒绝逻辑。
